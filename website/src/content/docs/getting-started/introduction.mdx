beacon is the **deterministic layer between your Python code and your LLM**. It gives you building blocks for the work around every model call: prompt templating, JSON extraction, tool-call parsing, schema validation, text normalization, content hashing, PII redaction and retry classification. All of them share one contract: **same input → same output, every time, on every machine.**

## Why it exists

The model is meant to be the only unpredictable part of an LLM application. In practice, the code around it adds unpredictability of its own:

- **Parsing** that relies on greedy regexes or "repair" libraries that guess what the model meant.
- **Validation** that silently coerces `"0.9"` into `0.9`, so model mistakes never show up.
- **Prompts** built with f-strings that user input can break out of.
- **Retries** with random jitter, so two logs of the same failure never match.
- **No tests**, because the output "isn't deterministic anyway".

beacon replaces that glue with small, pure functions written in Rust. Each has a published contract, edge-case tests and golden snapshots. You can then test everything except the model, and when something changes you can see exactly what.

<div class="beacon-guarantee">
  <span>✓</span>
  <p><strong>The promise:</strong> every block is a pure function. No hidden state, no I/O, no clock, no environment variables, no randomness. Its output (including error messages) is byte-identical across runs, operating systems, Python versions and patch releases. ## What beacon is not

- **Not an LLM client.** It never makes network calls. Use any client you like.
- **Not a repair tool.** Malformed output raises an error with a position. It is never "fixed" for you.
- **Not a cache or rate limiter.** Those are separate concerns; compose them with beacon if you need them.
- **Not a framework.** There's nothing to subclass and no runtime to adopt. Use one block or all eight.
