# v2.0 · Pillar A — Provenance ledger — what changed

Everything below is **uncommitted on `main`** for you to review and commit.
Nothing was committed, branched, PR'd, or published. No existing block output,
error code or message changed; the three gates (deterministic, provider-agnostic,
non-model) hold. Pure Python, built on the existing `hash_content` primitive — no
Rust changed, so no rebuild and no snapshot churn.

## What it is

A deterministic, content-addressed, **tamper-evident** record of what a pipeline
did — "prove what your pipeline did with this input," offline, with no model and
no network. The headline of the proposed v2.0 "verifiable" theme (Pillar A).

## Design decisions taken (recommended defaults)

- **Minimal scope** (hashes + `verify`), not signed records. Signing stays a
  future optional hook *outside* the deterministic core (noted in the docs).
- Built **on `Pipeline`** by extending `run_traced` into `run_recorded`, as the
  prompt recommends, rather than inventing parallel machinery.
- Ledger logic lives in **Python** on top of the cross-language `hash_content`.
  The chain algorithm is fully specified (and pinned by a test) so a future
  binding reproduces byte-identical roots — the actual JS/other-language port is
  deferred to the conformance pillar (D).

## API

- **`Pipeline.run_recorded(*args)` / `arun_recorded`** → `RecordedResult(output,
  ledger)`.
- **`Ledger`** — a hash chain of `LedgerRecord{index, op, input_hash,
  params_hash, output_hash, prev_hash, record_hash}`. `.root` is a byte-identical
  fingerprint of the whole run; `.as_dict()` / `Ledger.from_dict()` round-trip to
  JSON; `.with_meta(**kv)` attaches **sidecar** data (timestamps, host, run id)
  that no hash covers and that never affects verification; `core_version` and the
  `v1` format version are recorded.
- **`verify(ledger, inputs=None, *, pipeline=None)` → `VerifyReport`** — always
  checks chain integrity (offline tamper-evidence); also re-runs the pipeline and
  confirms every op / input hash / output hash when a pipeline + inputs are given.
  `report.ok` / `.chain_ok` / `.reproduced` / `.failures`; truthy when it holds.
- **`beacon.aio.verify`** mirrors it (sync-pipeline reproduction on a worker
  thread).
- Exported top-level: `Ledger`, `LedgerRecord`, `RecordedResult`, `VerifyReport`,
  `verify`.

## Chain algorithm (the cross-language spec)

```
record_hash = hash_content(["v1", index, op, input_hash, params_hash,
                            output_hash, prev_hash], length=32)
prev_hash   = "" for the first record, else the previous record_hash
root        = last record_hash
```

`params_hash` is `hash_content(None, length=32)` on the Pipeline path (a block's
params are folded into its op). `input_hash`/`output_hash` are `hash_content`
digests, or `None` for non-JSON-like values (which the chain still covers but
reproduction can't output-check).
