# beacon v2.0 — Verifiable & Streaming (proposed next major phase) · master prompt

You are implementing **v2.0**, the next *major* phase of **beacon** — a library
of deterministic, tested building blocks for AI pipelines. v0.1–v1.0 and the
adoption phase are done: the core blocks, `repair_json`, streaming
`parse_partial`, `extract_citations`, `detect_injection`, async `beacon.aio`,
the Cargo workspace (`beacon-core` on crates.io, `beacon-python`, `beacon-wasm`,
`beacon-js` on npm), the integrations, and snapshot / golden / record-replay
testing.

> **This phase is a proposal, not a written roadmap item.** The original roadmap
> ended at v1.0 + launch. Before building, the maintainer must confirm the
> **theme** (§4, decision 0). Everything below is designed to pass beacon's
> gates and extend its moat, but the direction is theirs to ratify.

---

## 0. Mission & the three gates

beacon's moat is a **determinism contract**: same input → byte-identical output
on every machine, forever, error messages included. v2.0's thesis: **turn
determinism into verifiability** — if the boundary is deterministic, you can
*prove* offline exactly what a pipeline did with a given input, stream it
incrementally, and run it byte-identically in any language.

Every addition must pass all three gates or not be built:

1. **Deterministic** — no clock, RNG, locale, env, network, or model in any
   block or in any *verified* record. (Wall-clock annotations may exist only
   *outside* the hashed, verified content.)
2. **Provider-agnostic** — at the boundary between model output and app code.
3. **Non-model** — never calls, scores, or embeds with a model.

## 1. Hard constraints (non-negotiable)

- **Git is the maintainer's.** Do not commit, branch, PR, or publish. All work
  stays on `main` as uncommitted edits; every external release and submission is
  the maintainer's. You prepare, they ship. (`never-commit` memory.)
- **"What NOT to build"** still holds: no chat client, constrained decoding,
  eval/scoring framework, RAG/vector store, agent framework, silent repair,
  ML PII, or Pydantic/Tenacity reimplementation. A provenance ledger is **not**
  an eval framework and must not score model quality — it records *what the
  deterministic boundary did*, nothing about whether the model was good.
- **Determinism of records**: the verified content of any ledger record is a
  pure function of inputs, op, params, and code version — reproducible on every
  machine. Anything non-deterministic (timestamps, host) is optional metadata
  carried *outside* the hash chain and never affects verification.
- **Cross-language parity is the acceptance bar**: any block or format added to
  `beacon-core` must produce byte-identical output across every binding, proven
  by a shared conformance corpus (§3.D).
- **No new unsafe; clippy denies unwrap/panic; fuzz every new parser.** Keep the
  full `pytest`, `ruff`, and `clippy` green at every step. Build recipe (Windows
  GNU): `RUSTFLAGS="-L native=C:/Users/knigh/AppData/Local/Programs/Python/Python314/libs" PYO3_USE_RAW_DYLIB=0 .venv/Scripts/python.exe -m maturin develop`; pure core `PYO3_USE_RAW_DYLIB=0 cargo test --no-default-features`.
- Reuse existing primitives — `hash_content` (BLAKE3), `Pipeline.run_traced` /
  `StepRecord`, `parse_partial`, the snapshot/golden format, and the v1.0
  cross-language golden corpus — rather than inventing parallel machinery.

## 3. The pillars

### A. Provenance / audit ledger (the headline)

A **deterministic, content-addressed, tamper-evident** record of what the
boundary did — "prove what your pipeline did with this input," offline.

- A record per block run: `{op, input_hash, params_hash, output_hash,
  core_version}`, all via `hash_content`. Records chain: each carries the hash
  of the previous → a Merkle-style deterministic log. A `Ledger` accumulates
  them; its root hash is a byte-identical fingerprint of the whole run.
- `verify(ledger, inputs) -> Report`: re-runs the recorded deterministic blocks
  on the given inputs and confirms every `output_hash` and the chain — a real
  proof, no model, no network. Tampering (any altered record) fails verification.
- Integrate with `Pipeline` (extend `run_traced` into a ledger-emitting
  `run_recorded`) and with the blocks directly. Timestamps/host, if wanted, are
  sidecar metadata outside the hashed content.
- Python + `aio` + JS parity; snapshot the ledger format (versioned, like the
  snapshot format). Compliance angle (auditable AI boundaries) — but ship it as
  a determinism feature, not a compliance product.

### B. First-class streaming engine (beyond `parse_partial`)

Incremental extraction / validation / redaction / tool-call detection over a
token stream, with deterministic checkpoints.

- `StreamParser` / `stream_json`: feed chunks, get progressive deterministic
  partial results + a completeness signal, building on `parse_partial`.
- **Chunk-boundary invariance** (the key property + test): the same bytes split
  into chunks *any* way yield the same sequence of committed results and the
  same final value. Fuzz it.
- Streaming redaction (never emit a secret across a chunk boundary) and
  streaming tool-call detection are high-value variants.
- Core (Rust) + Python + `aio` (async iterators) + JS (async iterables) parity.

### C. Broader language reach (Go, JVM, C ABI)

Extend the cross-language core beyond Python/JS:

- A stable **C ABI** over `beacon-core` (the FFI foundation), then **Go** (cgo
  or wazero/WASM) and **JVM** (Java/Kotlin via JNI or the WASM core) bindings.
- Each binding mirrors the block API and throws/returns beacon's error codes.
- Every binding must pass the conformance corpus (§D) byte-for-byte. Prefer
  reusing the WASM core where it keeps parity cheap.

### D. Conformance & determinism attestation

Make the moat provable as bindings multiply.

- A single **language-neutral golden corpus** (inputs + expected JSON outputs)
  committed once; a runner per binding asserts byte-identical results. Extend the
  v1.0 Python↔JS corpus to cover every block and every binding.
- A reproducible **determinism report** (what was tested, across which
  languages/platforms, with the core version) published on the docs site.

### E. Developer experience & ergonomics (make the package effortless)

A block can be perfectly deterministic and still be miserable to use. This
pillar is about the second thing: a developer who reaches for beacon should get
an obvious API, an error that says exactly what went wrong and what to do about
it, and introspection when they want it — with **zero** gate violations. It is
cross-cutting: apply it to everything the other pillars add (ledger, streaming,
new bindings) *and* retrofit the existing blocks.

- **Errors that diagnose, not just reject.** Every beacon exception already
  carries a stable `code` and a deterministic message. Make them actionable: a
  consistent shape of *what* failed, *where* (path / code-point offset into the
  input), the offending fragment, and a concrete next step ("missing `}` to
  close the object started at offset 12"; "field `age`: expected integer, got
  string"). Add an `.explain()` that returns the long-form human explanation —
  still deterministic, no color, no clock. Never let non-deterministic data
  (host, time, memory address) into a message or an `.explain()`.
- **Opt-in diagnostics — never ambient side effects.** A library that writes to
  stdout or the root logger on its own is both a footgun *and* a determinism
  trap (ordering, env, import time leak in). beacon must never do it. Instead,
  the caller opts in: blocks return structured diagnostic objects (the model is
  already there — `repair`'s repair log, `Pipeline`'s hash trace) and may accept
  an optional caller-supplied `on_event` / logger callback. All logging happens
  at the *caller's* edge; the hashed, verified content is untouched. Document
  the boundary in one sentence: "beacon never logs on its own — here is how to
  see everything it did."
- **Rich, readable result objects.** `RepairResult`, `StepRecord`, `Report`,
  `Ledger`, the streaming parser state, etc. get a good `__repr__` (and, where
  the runtime offers it, `_repr_html_` / a `rich` repr) so they summarize at a
  glance in a REPL, a notebook, and a log line — "repaired 3 (trailing_comma×2,
  truncated), incomplete=False".
- **Introspection surfaces.** A `beacon explain <code>` / `--explain` CLI mode
  and a `--verbose` that prints the deterministic diagnostic trace; a
  `beacon doctor` that reports versions, the pinned data versions (Unicode, hash
  encoding, snapshot format) and per-binding parity status; a `why` / `explain`
  accessor on a ledger `Report` ("record 3 failed: output_hash mismatch at op
  `extract_json`").
- **Typing & docs ergonomics.** Complete, precise type stubs; every public
  symbol with a docstring that states what it does, its determinism guarantee,
  and *what it does not do*; copy-paste-runnable examples; a one-import happy
  path; a small, obvious exception hierarchy.
- **Footgun guards (deterministic, opt-in).** Where a silent surprise is likely
  — truncated input treated as complete, a schema that can match nothing, a
  secret about to cross a stream boundary — surface it through the returned
  flags / diagnostics, never a hidden `warnings.warn` that depends on env or
  import order.

Stability rule: `code`s stay frozen forever. Changing an existing *message* is a
behaviour change — it belongs in this major line, recorded in the changelog with
updated snapshots, never slipped into a patch. Prefer *adding* `.explain()` and
structured fields over rewording the short, stable message.

## 4. Decisions the maintainer makes first

- **0 — ratify the theme.** Confirm "verifiable & streaming" is the v2.0
  direction, or redirect. Do not build until confirmed.
- **A — ledger scope**: minimal (hashes + verify) vs. signed records (adds an
  optional, caller-supplied signing hook — keep the signing *outside* the
  deterministic core).
- **B — streaming API shape**: stateless `stream_*` helpers vs. a stateful
  `StreamParser` object (recommend offering the object, built on the stateless
  core).
- **C — binding priority & mechanism**: which of Go / JVM / C-ABI first, and
  native-FFI vs. embedding the WASM core.
- **E — diagnostics channel & message freeze**: structured diagnostics object,
  an optional `on_event` callback, or both (recommend both — an object always, a
  callback for streaming / long runs); and whether to keep every existing short
  error message frozen in v2.0 and add all richness via `.explain()` + fields
  (recommended), or reword some messages as an explicit, snapshotted behaviour
  change.
- Each pillar can ship as its own minor release (v1.1, v1.2, …) under the v2.0
  umbrella; the maintainer sequences.

## 5. Definition of done (per pillar; the phase ships incrementally)

- **A**: deterministic ledger with a versioned, snapshotted format; `verify`
  catches any tampering; `Pipeline.run_recorded`; Python + `aio` + JS parity;
  non-deterministic data provably excluded from the verified hash.
- **B**: streaming engine with chunk-boundary invariance proven by fuzzing;
  parity across Python/`aio`/JS.
- **C**: at least one new language binding passing the conformance corpus
  byte-for-byte, via a stable C ABI or the WASM core.
- **D**: one language-neutral golden corpus + per-binding runners, all byte
  identical; a published determinism report.
- **E**: exceptions carry structured fields + `.explain()`; result objects have
  readable reprs; a `--explain` / `--verbose` CLI and `beacon doctor` exist; no
  block logs on its own (diagnostics are opt-in); complete type stubs and every
  public symbol documents "what it does not do"; any reworded message is
  versioned and snapshotted, `code`s unchanged.
- Across all: three gates upheld, no existing output/error changed, "What NOT to
  build" respected, suite + `ruff` + `clippy` green, and **nothing committed,
  branched, PR'd, or published by you** — changes left on `main` with a note of
  what you did and what the maintainer must run or release.
